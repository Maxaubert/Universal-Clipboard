# macOS clipboard backend (M5): how it works

Date: 2026-11-14. Crate: `uc-clip-mac`. Plan: sections 3.8, 3.9, 3.10, 6.4, milestone M5.

## What it does
- `MacClipboard` implements the `uc_clip::Clipboard` trait on one `NSPasteboard`.
- It takes a pasteboard by name:
  - `MacClipboard::general()`: the user's clipboard. Only the app uses it.
  - `MacClipboard::named(name)`: a private pasteboard. Tests use this.
  - `MacClipboard::from_env()`: the pasteboard named in `UCLIP_TEST_PASTEBOARD`, else the
    general one. Test builds of the agent set this variable (plan 6.4).
- The OS code builds only on macOS. The pure parts (`poll`, `types`) build and run on every OS.

## Watching for changes
- macOS has no change event. The agent polls `changeCount`. This reads no content and shows no
  prompt.
- `poll::Poller` picks the wait between polls:
  - 250 ms normally.
  - 100 ms for 1.5 s after a change (apps often write in several steps).
  - 500 ms after 10 minutes with no change.
- The first poll only sets the start point. A counter that goes down (pasteboard server restart)
  counts as a change.

## Reading
1. Read `changeCount`, then the list of types. The type list reads no content.
2. Sort the clip by its types:
   - Our marker `io.github.maxaubert.uclip.origin`: flag `has_marker`.
   - `org.nspasteboard.ConcealedType`, `TransientType`, `AutoGeneratedType`: flag `private`.
   - `public.file-url`, `NSFilenamesPboardType`, `com.apple.pasteboard.promised-file-url`:
     flag `has_files`.
   - `com.apple.is-remote-clipboard`: flag `remote` (a clip from another Apple device).
   - The type list cannot be read: the clip counts as private (plan 3.10).
3. If the clip has the marker, a private marker or a file, **the content is not read**. The
   engine skips such clips anyway, and a password is never read.
4. Else read:
   - `public.utf8-plain-text` with `stringForType`. AppKit also turns older text types (UTF-16,
     `NSStringPboardType`) into this.
   - `public.html` as UTF-8. UTF-16 with a byte order mark is turned into UTF-8. Other bytes
     are dropped (the text part still syncs).
   - `public.png` as it is. Else `public.tiff`, turned into PNG with `NSBitmapImageRep`. Only
     the first page of a multi-page TIFF. A TIFF that AppKit cannot read gives no image part.
5. Read `changeCount` again. If it changed during the read, start again (3 tries), then report
   `Busy`.

## Remote clips (plan decision 8)
- The backend only flags them (`Snapshot::remote`). The engine does not look at the flag yet.
- `set_read_remote_content(false)` makes the backend skip the content of a remote clip, so macOS
  does not fetch the data from the other device. Default: content is read. The agent sets this
  when decision 8 is made.

## Writing
- `prepareForNewContentsWithOptions(.currentHostOnly)` first, so Apple's Universal Clipboard does
  not send our clip to other Apple devices.
- Then the parts: text, HTML, PNG plus a TIFF copy (many Mac apps paste only TIFF), and our
  marker type with empty data.
- Text that is not UTF-8 is refused (`ClipboardError::Other("text-not-utf8")`).
- Returns `changeCount` after the write (echo layer 2).
- HTML without a charset gets `<meta charset="utf-8">` in front (`types::with_charset_meta`):
  AppKit (TextEdit, Mail, Notes) reads HTML with no charset as Latin-1. A read removes that exact
  prefix again (2026-11-14, found in the Mac review).

## Privacy setting (macOS 15.4 and later)
- `access_behavior()` returns the "Paste from Other Apps" setting, or `None` on older macOS.
- A named pasteboard always allows access. The general pasteboard may ask. The on-purpose first
  read and the settings row are agent work (M7) and need spike S2.
- On the general pasteboard, when the setting is Ask or Deny, `read` returns the types only, no
  content, so a background copy never shows a macOS alert. The agent shows its "paste-access"
  row instead. Default is still read (the first read is the one prompt).

## Tests
- Pure tests (every OS): poll timing, type sorting, HTML decoding.
- Real pasteboard tests (macOS only): each test makes its own named pasteboard
  `io.github.maxaubert.uclip.test.<pid>.<n>` and frees it at the end. They check that the name
  is not the general pasteboard. They never open the general pasteboard.
- Covered: text, UTF-16 text, HTML, PNG, TIFF to PNG (same pixels as the engine hashes them),
  PNG write with a TIFF copy, a broken TIFF, our marker, each private marker, file clips, remote
  flag on and content skip, `changeCount` and the poller, empty pasteboard, non-UTF-8 text, and
  the sync engine on top of the backend.
- Run on the Mac over `ssh mac` on 2026-11-14 (macOS 27.2): the named pasteboard works from an
  SSH session. Nothing appeared on screen and no prompt was shown.
- GitHub CI runs the same tests on `macos-latest`.
